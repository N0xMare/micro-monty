# The differences `cargo xtask durability` allows (docs/spec.md §5.1,
# clause 4; the lane D plan): FILE<TAB>MODE<TAB>COLUMNS<TAB>reason.
#
# Modes, each compared with the unparked native run: `parks` (parked every
# N fuel units in one process), `snapshot` (the same, a snapshot at every
# stop, the session going on), `restore` (each park restored in a new
# process); with `--cross-target`, `cross` (each restore on the other
# target), and `wasm`, `wasm-parks` and `wasm-snapshot` (the unparked and
# in-process modes on wasm32-wasip1). `restore-vs-snapshot` compares the
# `restore` chain with `snapshot` instead: a restored session must go on
# as the one that took the same snapshots. Columns: `report` (stdout, result,
# exception), `fuel` (the total spent), `digest` (the checksum of the
# session's image at the end, fuel cleared, clock pinned, counter
# entropy) and, for `cross` only, `refused` (the chain ended at a restore
# the other target refused for memory; nothing else is compared then).
#
# Removing: `cargo xtask durability --record` (and `--cross-target
# --record`) drops what no run differed in; it never adds an entry. Which
# park differs depends on the policy (before step 2, 463's `parks`
# digest differed at 1:1000 and not at 1:100), and entries are not keyed
# by policy, so `--record` runs the subset at both gates' policies, the
# landing tier's 1:100 and the release gate's 1:1000, beside 5:50
# (cross-target: 5:50, its only policy), and takes no filter or other
# policy. It writes only when every job finished (no crash or timeout)
# and differed only where this file records: a job that did not finish
# shows nothing, so its entries would look stale. One complete run is
# enough, since a build's report, fuel and digest do not depend on load,
# core count or the scratch path [M]. Each step of the
# deterministic-collection plan removes the entries it closes.
#
# Adding: only by hand, in the commit whose change makes the case differ,
# when the difference is one of the causes below (or a new cause the
# commit names and whose closing step it gives). Each line names its
# cause and the step that closes it, as the lines below do, and the
# commit message says which entries it adds and why. A difference that
# is none of these is a bug to fix, not an entry.
#
# Causes and the steps that close them:
#   accounting: bytes charged outside the arena, the VM's vectors among
#     them, follow `Vec` capacities and the target's word size, and an
#     image holds them as the target that wrote it counts them (the bytes
#     charged, the code loaded since the last reclamation), so the final
#     image follows the target: `wasm` and `wasm-parks`, which differ
#     alike since parks move nothing, and `wasm-snapshot` and `cross`
#     (step 4). Near the limit a collection falls where the target's
#     charges put it, so fuel follows the target too (own 535, 536), and a
#     park may not fit on the target that charges more: the `cross` chain
#     then ends there, in the `refused` column.
#   No native mode differs: a snapshot changes nothing in the session it
#   is taken from and a restore reserves and charges what the image's
#   session held, so `parks`, `snapshot`, `restore` and
#   `restore-vs-snapshot` have no entries (steps 3, 5 and 6 are closed).
