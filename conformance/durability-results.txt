# The differences `cargo xtask durability` allows (docs/spec.md §5.1,
# clause 4; the lane D plan): FILE<TAB>MODE<TAB>COLUMNS<TAB>reason.
#
# Modes, each compared with the unparked native run: `parks` (parked every
# N fuel units in one process), `snapshot` (the same, a snapshot at every
# stop, the session going on), `restore` (each park restored in a new
# process); with `--cross-target`, `cross` (each restore on the other
# target), and `wasm`, `wasm-parks` and `wasm-snapshot` (the unparked and
# in-process modes on wasm32-wasip1). `restore-vs-snapshot` compares the
# `restore` chain with `snapshot` instead: a restored session must go on
# as the one that took the same snapshots. Columns: `report` (stdout, result,
# exception), `fuel` (the total spent) and `digest` (the checksum of the
# session's image at the end, fuel cleared, clock pinned, counter
# entropy).
#
# Removing: `cargo xtask durability --record` (and `--cross-target
# --record`) drops what no run differed in; it never adds an entry. Which
# park differs depends on the policy (463's `parks` digest differs at
# 1:1000 and not at 1:100), and entries are not keyed by policy, so
# `--record` runs the subset at both gates' policies, the landing tier's
# 1:100 and the release gate's 1:1000, beside 5:50 (cross-target: 5:50,
# its only policy), and takes no filter or other policy. It writes only
# when every job finished (no crash or timeout) and differed only where
# this file records: a job that did not finish shows nothing, so its
# entries would look stale. One complete run is enough, since a build's
# report, fuel and digest do not depend on load, core count or the
# scratch path [M]. Each step of the deterministic-collection plan removes
# the entries it closes.
#
# Adding: only by hand, in the commit whose change makes the case differ,
# when the difference is one of the causes below (or a new cause the
# commit names and whose closing step it gives). Each line names its
# cause and the step that closes it, as the lines below do, and the
# commit message says which entries it adds and why. A difference that
# is none of these is a bug to fix, not an entry.
#
# Causes and the steps that close them:
#   collection points: where a collection starts depends on the fuel left
#     in a slice (`Vm::reset_ticks`), so parks move it (step 2);
#   snapshot collection: a snapshot collects in full and drops caches
#     (`prepare_snapshot`), so the session differs from the unparked one
#     (step 5); on a large heap a lazy sweep or a mark in flight at the
#     snapshot is lost too (step 6);
#   char cache: the char-position cache is cleared by every collection and
#     absent from the image (step 3);
#   accounting: bytes charged outside the arena, the VM's vectors among
#     them, follow `Vec` capacities and the target's word size (`wasm` has
#     no parks; step 4). A restore charges only what the image holds, so it
#     sheds the capacity a peak left (`restore-vs-snapshot`, own 534-536),
#     and a park near the limit may not fit on the target that charges
#     more: the `cross` chain then ends there, a `report` difference.
