# Spike S1: interpreter dispatch, results

Input to the bytecode-shape decision in docs/spec.md §8.1. This page reports
measurements only; it makes no recommendation. Every number on this page is
measured on this orb [M] unless it says otherwise. Source, exact commands and
raw outputs: `spikes/dispatch/` (README.md, `run_all.sh`, `results/`).

## Method

### Variants

Three bytecode designs, each with two dispatch mechanisms:

| Design | Model | Operands | Calls |
|---|---|---|---|
| stack | CPython / QuickJS | operand stack; `LOAD_FAST_LOAD_FAST`, fused `COMPARE_LT_JUMP_IF_FALSE`; methods as `LOAD_METHOD` + `CALL n` | `[callee, args]` on the stack; callee locals overlay the args (no copy); result replaces the callee slot |
| accumulator | V8 Ignition | implicit accumulator + frame registers: `Ldar`, `Star`, `LdaSmi`, `Add r` (acc = r + acc), `TestLessThan r` + `JumpIfFalse`, `GetNamedProperty`, `GetMethod`, ... | `CallUndefinedReceiver1 f a`, `CallProperty1 f recv a`: arguments copied into a new frame above the caller's; result in the accumulator |
| register3 | Lua 5 | three-address: `ADD a b c`, `LT_JMPF a b target`, `MOVE`, `GETATTR a b ic`, `SELF a b ic`, ... | `CALL a n`: callee in R[a], args in R[a+1..]; callee frame overlays the args (no copy); result in R[a] |

| Mechanism | Shape |
|---|---|
| match | `loop { match code[pc] { ... } }`; all handlers `#[inline(always)]` into one function; pc, base, sp/acc, code and frame-stack slices in locals (machine registers) |
| fntable | `static TABLE: [fn(&mut Vm) -> Flow; 256]`; loop calls `TABLE[code[pc]](&mut vm)`; VM registers live in memory behind `&mut Vm` |

Both mechanisms of a design are generated by one macro from one list of
handler functions, so the handler bodies are identical; only the call shape
differs. Python→Python calls push a frame and continue in the same loop in all
six (no Rust recursion per Python call).

### Shared substrate (identical in all six)

- **Value:** 8-byte NaN-boxed `u64` as spec §7.1: f64, SmallInt i48, Ref
  (kind byte + u32 offset), Special (None/False/True/Undefined), NativeFn.
- **Arena:** `Vec<Box<[u64]>>` of 2^17-word (1 MiB) segments, Ref =
  `seg << 17 | word`, every access bounds-checked through `get`/`set`; bump
  allocation, objects larger than a segment take consecutive segments, no GC.
  Reset (segments kept) before each run.
- **Objects:** function (code index + closure cells), cell, class (version +
  methods), instance (header with shape id + inline slots), list (len, cap,
  buffer; growth by doubling), dict (SmallInt keys, open addressing in the
  arena, Fx-style multiplicative hash, linear probing, resize at 2/3 load).
- **Frames:** one contiguous `Vec<Value>` frame stack (stands in for an arena
  segment), bounds-checked; a separate control stack of `{pc, base, code,
  func}` records for returns.
- **Semantics:** add/sub/lt/truthiness with inline SmallInt fast paths and
  `#[cold] #[inline(never)]` slow paths (floats, i48 overflow); `LOAD_GLOBAL`
  guarded by a globals-version field against an IC entry; attribute IC keyed by
  shape id → slot; method IC keyed by class version → function; `list.append`
  as a native reached through the method IC; ICs in a side table, empty at the
  start of every run.
- **Safepoints:** fuel counter decremented at every backward jump and every
  Python call; a `#[cold]` path refills it (quantum 10,000), counts refills and
  records the pc. Ticks are identical across all six variants for every kernel
  (checked in `results/bench_checked.txt`).

### Fairness rules

- Only bytecode format, operand access in handlers and dispatch differ.
  Object layouts, IC logic, slow paths, natives, safepoint logic and the
  frame-push/pop code are shared functions.
- One encoding scheme for all designs: 1-byte opcode, u8 operands, u16
  absolute jump targets, written by one assembler with labels and a per-design
  instruction-length table (register3 is therefore variable length, not Lua's
  fixed 32-bit words).
- Kernel bytecode is hand-assembled as a straightforward compiler for each
  design would emit it, with registers allocated as Lua's compiler would. Same
  rules for all: no immediate-operand arithmetic (no `AddSmi`/`ADDI`; small
  ints are one load-immediate instruction), same loop shape everywhere (a
  range-specialised `FOR_ITER` at the loop head that exits forward, a
  fuel-ticking backward jump at the tail), `range(n)` is a `LOAD_GLOBAL` +
  call that returns the iterator object (no separate `GET_ITER`).
- Per the brief: stack gets `LOAD_FAST_LOAD_FAST` and a fused compare-and-jump;
  register3 gets a fused `LT_JMPF`; accumulator uses Ignition's unfused
  `TestLessThan` + `JumpIfFalse`. The accumulator bytecode applies the one
  peephole Ignition's register optimizer always applies (no `Ldar r` right
  after `Star r`).
- Each design implements only the opcodes the kernels use: 24 (stack),
  24 (accumulator), 21 (register3).
- Benchmarks run one at a time, pinned with `taskset -c 2`. Each variant runs
  one untimed verification round, then 15 timed rounds; each round runs every
  (kernel, variant) pair once, interleaved, so drift hits all variants alike.
  Timer: `Instant` around the dispatch loop only (heap reset, setup and frame
  construction are outside it).

## Caveats

- **Run-to-run noise.** A second process running the same binary
  (`results/bench_checked_run2.txt`) changed medians by −6% to +4% for every
  kernel except dict on all match variants, and by +0% to +7% on the fntable
  variants except register3/fntable closure (+18%) [M]. The dict kernel moved
  +9% to +34% and has the widest median-to-min spread within a run (median up
  to 1.37× the min, stack/fntable) [M]; its table (8 MiB at 200k entries) does
  not fit in L2. register3/fntable loop measured 49.0 ms median in an earlier
  run of the same binary (not kept in `results/`) and 41.5 ms here [M].
  fntable medians moved between processes by up to ~18% while match medians
  outside dict stayed within 6%, which is consistent with address-layout
  (ASLR) effects on indirect-call prediction; not verified without counters.
- **Spike, not an engine.** No GC, no bigint (i48 overflow becomes a float in
  the slow path; no kernel overflows), no exceptions (an error stops the run),
  no shape transitions, only the opcodes the kernels need (21–24 per design; a
  full engine has several times more, which changes register allocation in the
  big `match` function and the code size). The handler code sizes are for
  these subsets only.
- **`match` codegen is fragile.** Passing `Vm` by value left it in caller
  memory (pc stored on every dispatch); `run_match` rebuilds it as a local so
  LLVM keeps the fields in registers. This fix is in the shared macro, so all
  three designs have it. The loop back-edge still shows register shuffling and
  a stack spill of the frame-stack pointer (inspected with `objdump` on
  register3).
- **Checked operand reads scale with operand bytes.** Every u8 operand read is
  a separate bounds check on the code slice, and every register operand a
  second check on the frame stack. register3's hot instructions carry up to
  four operand bytes and three register operands (`ADD a b c`), so this
  weighs most on it (highest ns/instruction above); the unchecked table
  bounds what a decoder with fewer checks could gain.
- **Calling conventions differ by design** (allowed as operand access):
  accumulator copies arguments into the new frame and reads the caller's frame
  size on each call; stack and register3 overlay arguments in place. register3
  needs `MOVE`s to build the call window (closure: 3 `MOVE`s per iteration),
  as Lua does.
- **Superinstruction set is a choice.** Only those named in the brief/spec
  exist (stack: `LOAD_FAST_LOAD_FAST`, compare-and-jump; register3: `LT_JMPF`;
  accumulator: none). Not measured: `STORE_FAST_LOAD_FAST`, immediate
  arithmetic (`AddSmi`, `ADDI`), compare-with-constant, Lua's bottom-tested
  `FORLOOP` (one fewer dispatch per iteration for any design), Lua's fixed
  32-bit instruction words.
- **Reference engines do more work and differ in semantics.** CPython and
  QuickJS have reference counting/GC, real exceptions and bigint/float
  promotion. In JS there is no `range` (a counted `for` loop), the dict is a
  `Map`, and numbers are int32 or float64, so the loop, attr, list and dict
  sums continue in float64 after 2^31. qjs was built with `-O2` and debug info
  by its own Makefile.
- **Arena reuse.** The arena is reset between runs and its segments reused,
  so first-touch page faults fall in the untimed verification round. The fuel
  counter and the IC table live in memory in every variant.
- **One machine, one compiler.** KVM guest, Xeon model 106, rustc 1.99.0 /
  LLVM 23.1.1; results may differ on other CPUs or compiler versions.

## Observations

Facts from the tables above; no recommendation.

- `match` was faster than `fntable` for every design and kernel. The
  fntable/match median ratio was 1.33–1.58 for stack, 1.36–1.64 for
  accumulator and 1.19–1.43 for register3 [M].
- With `match` dispatch, accumulator medians were lower than stack on all
  seven kernels: −4% (fib), −21% (loop), −18% (closure), −8% (method) on the
  call and loop kernels, −13% to −27% on attr, list and dict [M].
- With `match` dispatch, register3 medians were lower than stack on fib (−3%),
  loop (−21%), attr, list and dict (−7% to −18%), and higher on closure (+9%)
  and method (+4%) [M].
- With `fntable` dispatch, register3 was the fastest design on fib, loop,
  attr, list and dict, accumulator on closure and method [M].
- register3 dispatched 0.50–0.90× the stack design's instructions, accumulator
  0.71–1.15× (accumulator dispatched more than stack only on fib, 1.15×) [M].
- Wall time per dispatched instruction (match) was 2.2–3.1 ns for stack,
  2.1–3.4 ns for accumulator and 3.5–4.8 ns for register3, excluding dict [M].
- Bytecode was larger than stack's in every kernel for accumulator
  (1.19–1.43×) and in five of seven for register3 (0.96–1.43×) [M].
- Dispatch code size with `match`: 6,123 B (stack), 6,291 B (accumulator,
  +2.7%), 6,532 B (register3, +6.7%); with `fntable` 6,823 / 7,632 / 7,706 B
  [M].
- Removing bounds checks cut medians by 6–29% across variants and kernels
  (one exception: accumulator/match dict, +2%). register3/match gained the
  most of the six variants on every kernel except dict (−18% to −29%);
  stack/match gained the least on fib (−6%) and closure (−12%) [M].
  Unchecked, register3/match was 15% below stack/match on fib and
  accumulator/match 27% below it on closure [M].
- Against the reference engines on this orb, stack/match's median was
  0.39–0.66× CPython 3.12's on six kernels and 1.02× on dict, and 0.43–0.97×
  qjs's on all seven [M]. accumulator/match had the lowest median of the three
  match variants on every kernel: 0.31–0.75× CPython and 0.31–0.93× qjs [M].
